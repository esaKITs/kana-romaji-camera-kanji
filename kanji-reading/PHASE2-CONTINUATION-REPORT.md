# Kana → Romaji Camera 第二弾：評価再設計・軽量Sudachi比較・Still最小試作

2026年10月21日 / esaKITs

## 結論

依頼された旧30例の見直し、約100例の評価セット、辞書分離型Sudachiとの実行比較、OCRを含むStill最小試作を作成しました。第一弾のmain・アプリソース・公開設定・UIには変更を加えていません。3モードは「あア漢／ア漢／漢」のままです。開発成果はすべて開発ブランチ内の`kanji-reading/`にあります。

**解析器の最終採用は保留を推奨します。** 基本語は両者とも良好ですが、助数詞・日付の読みを生成する処理が必要です。エンジンの選択だけでは「三本」の誤読を解消できません。軽量Sudachiでは起動を速くできましたが、辞書とWASMメモリは大きく、スマートフォンでの採用判断には不足があります。

## 1. 旧30例の修正

- **No.17 江崎**：通常の正答率から除外。本人の読みが与えられていない場合の固有名詞の保留として別に検証しました。本人の読みが「エサキ」であっても、一般の姓「エザキ」を辞書から選ぶだけで人物の同定はできません。
- **No.30 龘**：通常の正答率から除外。「読みのない漢字」とは扱いません。今回の辞書で読みが得られない場合の未登録・未知語処理として記録しました。
- **日本語・明日等**：複数の成立する読みを許容します。日本語はニホンゴ／ニッポンゴ、文体未指定の明日はアシタ／アス／ミョウニチを登録しました。
- 元の文だけで意味を一意に限定できない生物・人気・上手の例も、別の解釈を直ちに誤答にしません。したがって、修正後スコアの上昇を意味・文脈解析の改善とは解釈しません。

通常評価の分母は28例です。修正後の結果はKuromoji 23/28、今回の軽量Sudachi 27/28でした。旧報告の辞書内包版Sudachiとは別実装・別辞書です。この小規模セットだけでは助数詞の問題が見えにくいため、以下の100例へ拡張しました。

実データ：[`lab/original-30-reviewed.json`](lab/original-30-reviewed.json)、別枠：[`lab/special-cases.json`](lab/special-cases.json)、実行結果：[`results/v2-original-30-review.json`](results/v2-original-30-review.json)。過去の生の実測結果は履歴として残しています。

## 2. 新しい100例と正答の確認方法

| 分類 | 件数 |
|---|---:|
| 基本語 | 30 |
| 活用・送り仮名 | 12 |
| 複合語 | 12 |
| 読みの異形・文脈 | 12 |
| 助数詞（本・杯・匹・人・階・冊） | 24 |
| 日付・月・時刻・分 | 10 |
| 合計 | 100 |

文章は自作しました。一般語の評価に、人物固有の読みや辞書未登録文字の「保留成功」を混ぜていません。

正答は解析器の出力を正解として決めたものではありません。独立したJMdictとの機械照合と文法的な読みの点検を実施し、**80例は見出し語と許容読みを直接照合、12例は原形を照合したうえで活用形を確認、8例は助数詞の音変化として確認**しました。本・冊・人の基礎形は国際交流基金の数え方の表も参照しました。杯・匹等の8例は独立辞書の完全一致見出しによる照合とは区別して記録しています。

これは独立した第二の専門家によるアノテーションではありません。また、助数詞・日付を重点配置したセットであり、日本語全体の平均正答率を推定する無作為標本でもありません。文脈だけでは一意に定まらない例に複数読みを認める一方、その例を意味の読み分け成功の証拠にはしません。

「三本」はサンボンを正答とし、サンホン／サンポンは誤答です。十本等ではジュッ／ジッの異形を許容します。舞台の上手は「舞台の右側を上手と呼びます」と文を具体化しました。

### 基本的な助数詞の問題

| 語句 | 許容する読み | Kuromojiの候補 | 軽量Sudachiの候補 |
|---|---|---|---|
| 一本 | イッポン | イチホン | イチポン |
| 三本 | サンボン | サンホン | サンポン |
| 六本 | ロッポン | ロクホン | ロクポン |
| 三杯 | サンバイ | サンハイ | サンバイ |
| 三匹 | サンビキ | サンヒキ | サンヒキ |
| 一人 | ヒトリ | イチニン | ヒトリ |
| 四人 | ヨニン | ヨンニン | ヨンニン |
| 二十日 | ハツカ | ニジュウニチ | ニトウカ |

これはローマ字の綴りの問題ではなく、数字と助数詞・日付をまとめて発音形にする段階の問題です。100例の正答表に合わせた置換を、解析器の素の結果へ混ぜていません。

### 表示を保留した場合

既存の試作保留条件（固有名詞・未知読み・数詞／日付・既知の曖昧語等）を適用すると、表示候補はKuromoji 56/100、軽量Sudachi 55/100となり、このセットで表示対象に残った候補には誤読がありませんでした。ただし、**未評価語でも誤読ゼロになるという保証ではありません**。保留によって相当数の正しく読めた例も表示できなくなります。製品の処理率として満足できる状態ではなく、保留と補正の改善を別に評価する必要があります。

## 5. 容量・速度・メモリ

| 実測項目 | Kuromoji | 軽量Sudachi |
|---|---:|---:|
| Chromium初期化（ローカルHTTP） | 0.86秒 | 0.88秒 |
| Node初期化 | 0.43秒 | 0.28秒 |
| Node RSS増分・OCRなし | 352.8MiB | 373.2MiB |
| 配布容量 | 圧縮辞書16.97MiB＋JS約0.29MiB | 辞書117.25MiB＋WASM約2.01MiB＋JS約12KiB |
| 展開後辞書／WASM領域 | 辞書約95.62MiB | WASM linear memory約249.69MiB |


ブラウザの初期化はローカルHTTP、キャッシュを保存しない設定での1回の例です。モデル配信の実回線やスマートフォンの起動時間ではありません。Nodeとブラウザの値も直接同一視しません。

Chromiumでは専用WorkerのJSヒープとArrayBuffer等の領域もCDPで測定しました。KuromojiはJSヒープ約39MiB・backing storage約90MiB、軽量SudachiはJSヒープ約1MiBに加え、WASM linear memoryが約250MiBです。これらは計測対象が違うため、不正確な合計値にはしていません。

ブラウザ全プロセスのRSS/PSSは、この実行環境では正しいPID対応を取得できず**未測定（null）**です。0MBとして報告していません。iPhone Safari／Android実機のメモリも未測定です。

「Small」「軽量」という名称でも辞書が十分小さいとは限りません。今回の生辞書は約117MiBで、実行時に大きなWASM領域を使います。GitHubの単一ファイル制限を考慮し、試作では8MiBずつのチャンクとハッシュ検証で取得しています。チャンク化で解決するのは配信時のファイルサイズであり、端末のメモリ量ではありません。

## 6. Still最小試作

**実際のMeikiOCRを動かした画像入力の試作**を作成しました。製品カメラUIへの統合や公開はしていません。ソース：[`still-prototype/`](still-prototype/)、再実行手順：[`lab/V2-README.md`](lab/V2-README.md)。

処理は、画像→OCRの行・文字座標→ふりがな候補の幾何対応→切り出し画像の拡大再OCR→共通読み推定→既存ローマ字処理→ラベル描画です。画像・OCR文字列を外部サーバーに送る処理はありません。

### 実行した画像試験

| テスト画像 | 確認できたこと |
|---|---|
| 学校で本を読みます／コーヒーを飲みます | 画像OCRと漢字・かな読みの候補表示 |
| 学校＋がっこう | 上側の小さいかなを座標で対応付け、別OCRでも一致。学校に1ラベル、ふりがなに重複ラベルなし |
| 生物＋なまもの | 解析器の分割境界と異なる漢字列でも、対応確認したふりがなを語群に優先適用 |
| 食べる／読みました | 3モードすべてをOCR結果で確認。「漢」では食／読だけを対象にし、送り仮名を残す |

入力はNoto Sans JPで作った横書きの文字画像です。実際のOCRは通していますが、紙を撮影した実写画像やスマートフォンのカメラ試験ではありません。すべての画像で3モードの対象選択を確認しました。

生物の画像では、OCR本文が「牛物」と返りました。ふりがなの再認識が一致したため、画像上のその漢字列にnamamonoを表示できましたが、これは「生」の文字認識が正しかったという意味ではありません。原文誤認識と読み補助の効果を分けて記録しています。

同時ロードしたStill試作でもWorkerのメモリ構成を測定しました。読みWorkerのbacking storageは約171MiB、OCR Workerでは約68MiBでした。これにWASM領域等が関わり、GC前の一時領域も含むため、足し合わせてアプリ全体の使用量・ピークとはしていません。初期化の実測例は約2.35秒ですが、ローカル配信での値です。

実測JSONにはOCRの全行・文字座標、ふりがなの再照合結果、各モードのラベル候補と描画結果を保存しました。未確定のふりがな候補は独立したローマ字ラベルにせず、無理な対応付けや重複を避けています。部分ルビ等を網羅する実装ではありません。

最小描画は白い試験用紙に限定し、前方／後方の空白、通常幅、限定した横圧縮を試しています。狭すぎる場合や衝突する場合は描画を保留します。「本」など、読み候補があっても描画を保留した例が残っています。一般の背景色処理、完全な行単位の空間配分、2行表示、文字の傾きは未統合です。

## 7. 検証状況と未解決点

- 新規・既存の研究用契約テスト21項目合格。正答率の分母、複数読み、source offset、3モード、送り仮名、ふりがなの重複・分割境界・不確実対応を含みます。
- 第一弾の既存テスト194項目合格。第一弾のソース・UI・公開workflowに差分はありません。
- Chromium内で両方式の100例を実行し、Nodeと同じ候補読みの集計を確認しました。
- Still試作では4画像の実OCRと3モードを実行。外部リクエスト0、GET以外0、ページ例外0を確認しました。
- 未確認：物理iPhone Safari／Android Chrome、長時間動作、復帰、実写の照明・傾き・小さいルビ、多段の部分ルビ、全体の最悪メモリ、Liveとの共有・安定化。
- 複雑な送り仮名・熟字訓の一部対応など、読みと文字位置を安全に対応付けできない部分は保留します。
- 既存のローマ字規則は変更していません。表示上の語の結合、語境界をまたぐ撥音等の完全な統合検査は残ります。
- ソース・版・辞書・ハッシュ・依存関係を記録しました。ビルド経路により生成WASMのバイト列が変わる場合があるため、セットアップは実際のハッシュを記録し、辞書とJSの既知ハッシュは厳密に照合します。

## 8. 次の推奨案・承認事項

1. **解析器は現時点で最終採用しない**ことを推奨します。候補を両方残し、次の数詞処理と端末負荷を比較します。
2. 次に、数詞＋助数詞／日付をひとまとまりで発音形へ変える独立処理を試作します。今回の100例にだけ合わせた修正にせず、別の数字・複合数・アラビア数字表記・文脈を使う追加セットで確かめます。ローマ字変換規則は維持します。
3. ふりがなの処理は、正しく認識できた場合を優先し、部分的・不確実な対応の保留を実写で点検します。現試作をそのまま実用の精度と扱いません。
4. UI変更については、今回、採用・実装承認を求める段階へ進めていません。第一弾UIは維持し、第二弾の製品UI案を提示した時点で承認を求めます。研究用の画像入力ページを正式UIとはしていません。
5. 第一弾の変更、第二弾の本番公開、解析器の最終採用は実施していません。最終採用・製品UI変更・本番公開はいずれも個別の承認後に行います。
