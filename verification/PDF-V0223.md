# v0.2.23 PDF import and PNG/PDF export verification

Implementation and limitations: `docs/PDF-IMPORT-EXPORT.md`.

Local Chromium end-to-end tests pass through both real OCR engines:

- Open a three-page sample PDF through the app's new public sample button.
- Select original pages 1 and 3, cancel conversion, then retry the selection.
- Convert selected pages through the unchanged existing OCR/reading pipeline.
- Set original-image visibility to 25% and enable guides. The decoded PNG's
  1334×1667 RGBA SHA-256 matches the actual output canvas exactly. Controls,
  zoom/pan and guide overlays are not exported.
- Change to macron spelling without changing the OCR snapshot. Export selected
  pages only; reopen with pdf-lib and require two pages in source order, with
  physical sizes 360×180 and 320×400 points.
- Navigate a cached page, then select /Rotate=90 page 2. Its saved image PDF
  is 360×240 points, matching the PDF.js displayed viewport orientation.
- A corrupt replacement PDF must leave the valid converted document available.
- Reopen the actual exported PDF through PDF.js and require two selectable pages.
- Return to an ordinary image Still and save its one-page PDF at 1125×465 pt.

Poppler rendered the actual selected-page and rotated PDFs. The page images
were inspected: content, original layout/white margins, opacity choice and
macrons are retained, with no toolbar, guide or page-index overlays. Exports
are raster images, not searchable text PDFs. This change does not claim to
improve the OCR accuracy of rasterized PDF text or add vertical/rotated OCR.

The first reopen test caught that current PDF.js exposes worker cleanup on
PDFDocumentLoadingTask rather than PDFDocumentProxy. A small facade now owns
loadingTask.destroy(); the same reopen test passes rather than being skipped.

State tests cover source-order selection, no empty exports, per-resolution
cache readiness, raw snapshot preservation, absence of retained render canvases,
cancellation ownership, document replacement, oversized-page rejection before
canvas allocation, and saved filenames. Existing Live tests run the real new
controller binding inside their existing DOM/engine harness.

The local full suite has only the pre-existing missing generated Sudachi module
failure. GitHub Actions must build the pinned research assets and pass all 157
unit tests plus original browser/parity/counter/Still/Live tests before release.
The PDF workflow also runs through Linux/macOS WebKit. A physical iPhone remains
an independent validation target; no such success is claimed here.
